# Meally: architecture

The research behind each decision is in [01-research.md](01-research.md).

## Overview

```
apps/web        React 19 + Vite SPA (TypeScript, Tailwind CSS v4, TanStack Query, React Router)
apps/server     Hono on Node 24, Drizzle ORM, SQLite (better-sqlite3); serves /api and the built web app
packages/shared zod schemas, API types, feature-flag registry, ingredient parser, unit conversion
```

One Docker image runs the server, and the server also serves the built SPA. All data is under `/data`: `meally.db`
plus `images/`.

## Decisions

| ID | Decision | Why (short) |
|---|---|---|
| A1 | TypeScript monorepo with npm workspaces | One language end to end. Types and zod schemas are shared between client and server. npm comes with Node, so there's nothing extra to install. |
| A2 | Hono server on Node | Small, fast, built on web standards, with typed routes. It has middleware for cookies, CORS and secure headers. |
| A3 | SQLite through Drizzle, migrations with drizzle-kit | Nothing extra to run (G5). WAL mode copes with concurrent users. FTS5 gives search. Drizzle also supports Postgres if we add it later. |
| A4 | Our own session auth: scrypt hashes (`node:crypto`), an httpOnly SameSite=Lax session cookie with the token hashed in the DB | Few dependencies, easy to audit. API tokens (F22) use the same table design. |
| A5 | React 19 + Vite + TanStack Query + React Router | A mainstream stack that's fast to build. Query handles cache, retries and optimistic updates. |
| A6 | Tailwind CSS v4 with our own components on Radix primitives (shadcn-style, written in this repo) | Modern look with accessible dialogs, menus and popovers, and no heavy UI kit. |
| A7 | Design tokens as CSS variables (OKLCH), light and dark themes, `prefers-color-scheme` with a manual override | Consistent theming and AA contrast. |
| A8 | Vitest for unit and API tests, Testing Library for components, Playwright for a few end-to-end flows | Fast and familiar. |
| A9 | Images stored on disk and resized with `sharp` to WebP at 3 sizes | Lighter than storing blobs in the DB. Cards load quickly. |

## Feature flags

- The registry lives in `packages/shared/src/features.ts`. Each entry has a `key`, `label`, `description`, `default`
  and `dependsOn`. It is the only list of flags.
- Each flag is resolved in this order:
  1. Env `MEALLY_FEATURE_<KEY_UPPER_SNAKE>` = `on` | `off`. This locks the flag, and the admin UI can't change it.
  2. Admin override in the `feature_flags` table.
  3. The registry default.
  4. If any flag in `dependsOn` is off, this flag is off too.
- Server: `requireFeature('meal-plan')` middleware on every route group of a feature. A request to a disabled feature
  returns `404 {"error":"feature_disabled"}`.
- `GET /api/features` returns the resolved map. The web app reads it with `useFeature(key)` and `<Feature on="key">`,
  which hide navigation, routes and buttons.
- Every feature folder registers its server routes and web routes, each behind its flag.

## Code layout

```
apps/server/src/
  app.ts                 builds the Hono app and mounts features
  db/schema/<feature>.ts Drizzle tables, one file per feature
  db/migrations/         generated by drizzle-kit
  features/<feature>/    routes.ts, service.ts, *.test.ts
  lib/                   auth, errors, rate-limit, images, config
apps/web/src/
  app/                   shell, router, providers
  ui/                    design-system components (Button, Card, Sheet, Dialog, ...)
  features/<feature>/    pages and components for one feature
  lib/                   api client, hooks
packages/shared/src/
  features.ts, schemas/<feature>.ts, ingredients/, units/
```

## API conventions

- JSON under `/api/v1`. Errors look like `{ "error": "<code>", "message": "..." }`.
- Lists use cursor pagination: `?limit=&cursor=` returns `{ items, nextCursor }`.
- Every row has `householdId`. Every query filters on the caller's household (tenant isolation, G3).
- Request bodies are validated with zod schemas from `packages/shared`.
